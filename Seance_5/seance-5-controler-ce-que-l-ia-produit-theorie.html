Chapitre 1 sur 6
📖Pourquoi lire ce que l'agent a écrit

Depuis la S3, un agent modifie plusieurs fichiers d'un coup. Pendant la phase d'autonomie, il a probablement produit des centaines de lignes. Ce code compile, l'écran s'affiche… mais « ça marche » ne veut pas dire « c'est correct », ni « c'est sûr », ni « je saurai le corriger ».

Objectif du chapitreSavoir lire un code que vous n'avez pas écrit, en suivant le chemin des données et le diff, pour être capable de l'expliquer, de le corriger et de le défendre à l'oral.

Le code généré est du code non relu

Un modèle produit du code plausible : il ressemble à ce qu'on trouve dans des milliers de projets. Mais il ne connaît pas vos contraintes réelles, il peut inventer une fonction, dupliquer une logique existante, laisser un reste d'essai précédent ou contourner un problème au lieu de le résoudre. Relire n'est pas de la méfiance : c'est votre travail de développeur quand vous déléguez en N3 ou N4.

Je ne commite pas ce que je ne comprends pas.

Si vous ne pouvez pas expliquer ce que fait une ligne, vous ne pouvez ni la corriger, ni la justifier devant le jury. Demandez une explication, simplifiez, ou rejetez.

🧭Une stratégie de lecture : suivre les données

Ne lisez pas les fichiers dans l'ordre alphabétique. Partez de ce que fait l'utilisateur et suivez la donnée jusqu'à la base, puis jusqu'au retour à l'écran.

1Partir de l'entrée utilisateur : un formulaire, un bouton, une URL, un champ de recherche.
2Suivre le flux de données : composant client, Server Action ou Route Handler, client Supabase, table, politique RLS.
3Suivre le retour : réponse, gestion d'erreur, rafraîchissement de l'affichage (revalidatePath, état local).
4Noter les zones floues et demander à l'IA de les expliquer ligne par ligne.

Exemple CinéList : « Ajouter à ma watchlist »

Bouton Ajouter→Server Action addToWatchlist→supabase.from('watchlist_items').insert()→Politique RLS→revalidatePath('/watchlist')

À chaque flèche, posez une question : d'où vient le user_id inséré ? Est-il lu côté serveur depuis la session ou envoyé par le navigateur ? Que se passe-t-il si l'insertion échoue ? Le film peut-il être ajouté deux fois ? Pour GameBacklog, même logique avec le changement de statut « à jouer → en cours » ; pour CampusHub, avec l'inscription à un événement complet.

Lire le diff plutôt que tout le projet

Après chaque tâche de l'agent, lisez ce qui a changé, pas tout le dépôt. git diff montre les modifications non indexées, git diff --staged celles déjà ajoutées, et git add -p vous fait valider chaque morceau un par un avant le commit. Les lignes préfixées par + sont ajoutées, celles par - supprimées.

Que regarder en priorité dans un diff ?
  • Les fichiers modifiés qui n'ont rien à voir avec la tâche demandée (hors périmètre).
  • Les suppressions : l'agent a-t-il retiré une vérification, un test ou une gestion d'erreur ?
  • Le fichier package.json : une nouvelle dépendance est-elle apparue ?
  • Les fichiers de migration SQL : une politique RLS a-t-elle été modifiée ou désactivée ?
  • Les fichiers .env* : ils ne doivent jamais apparaître dans un diff commité.
🔎Ce qu'il faut repérer

🪦 Code mort

Fonctions jamais appelées, imports inutilisés, composants d'un essai abandonné, blocs commentés. Ils brouillent la lecture et trompent l'agent aux tâches suivantes.

👯 Doublons

Deux fonctions formatDate, deux clients Supabase créés différemment, la même requête copiée dans trois pages. Une correction faite à un endroit sera oubliée à l'autre.

📦 Dépendances inutiles

Une bibliothèque installée pour une seule fonction que JavaScript ou Next.js fournit déjà (dates, requêtes HTTP, identifiants). Chaque paquet ajoute du poids et de la surface d'attaque.

🧷 Valeurs en dur

Un identifiant utilisateur de test, une URL locale, une couleur hors DESIGN.md, une clé écrite directement dans le code.

🚧 Faux raccourcis

Un try/catch qui avale l'erreur, un // TODO, un as any, une donnée simulée laissée à la place de la vraie requête.

🧩 Hors périmètre

Des fichiers modifiés sans lien avec la tâche : l'agent a « amélioré » autre chose au passage, sans que vous l'ayez demandé.

Faire expliquer le code par l'IA

Contexte : projet CinéList, Next.js App Router + Supabase.
Rôle : tu es un développeur senior qui explique à un étudiant.
Action : explique ligne par ligne le fichier app/watchlist/actions.ts.
Contraintes : pour chaque bloc, dis d'où viennent les données, où elles vont,
et signale tout code mort, doublon ou dépendance inutile. Ne modifie rien.
Format : tableau Ligne(s) | Ce que ça fait | Question ou risque.

❌ À éviter

Accepter tous les changements de l'agent parce que la page s'affiche, puis faire un seul commit « update ».

✅ À faire

Lire le diff, faire expliquer les zones floues, supprimer le code mort, puis commiter par petites unités compréhensibles.

Chapitre 2 sur 6
🐞Une méthode avant un prompt

Face à un bug, le réflexe du débutant est de coller « ça marche pas » dans le chat. Résultat : l'IA devine, modifie cinq fichiers, et le bug change de forme. Déboguer, c'est d'abord une méthode ; l'IA accélère chaque étape mais ne la remplace pas.

Objectif du chapitreReproduire, isoler et documenter un bug, puis donner à l'IA exactement ce dont elle a besoin pour proposer des hypothèses et une correction vérifiable.
1Reproduire : trouver les étapes exactes qui déclenchent le bug à chaque fois. Un bug non reproductible ne peut pas être vérifié comme corrigé.
2Isoler : réduire au cas minimal. Le bug arrive-t-il avec un seul film ? Uniquement pour un utilisateur non connecté ? Uniquement sur mobile ? Uniquement en production ?
3Lire l'erreur : le message exact et la stack trace, pas seulement « erreur 500 ».
4Formuler des hypothèses classées de la plus probable à la moins probable.
5Corriger une chose à la fois, puis revérifier avec les étapes de reproduction.
🛠️Où regarder : les bons outils

Dans une application Next.js / Supabase, l'erreur ne s'affiche pas toujours là où on la cherche. Le code serveur (Server Components, Server Actions, Route Handlers) écrit ses logs dans le terminal où tourne npm run dev, pas dans la console du navigateur.

OutilCe qu'il montreExemple fil rouge
Console du navigateur (DevTools)Erreurs JavaScript côté client, avertissements React, erreurs d'hydratationGameBacklog : « Cannot read properties of undefined (reading 'title') » quand la liste est vide

Lire une stack trace

Une stack trace est la pile des appels au moment de l'erreur. Lisez d'abord le message (la première ligne), puis cherchez la première ligne qui pointe vers vos fichiers (app/, components/, lib/) plutôt que vers node_modules. C'est en général là que se trouve la cause, ou au moins le point d'entrée.

⛔ Piège Supabase classique Quand une politique RLS bloque une lecture, Supabase ne renvoie pas d'erreur : il renvoie un tableau vide. « Ma liste est vide » peut donc être un problème de droits, pas de données. En revanche, une insertion refusée renvoie un message du type new row violates row-level security policy for table "watchlist_items".
💬Donner à l'IA ce dont elle a besoin

Un bon prompt de débogage contient quatre éléments : l'erreur exacte, le contexte, le comportement attendu et ce que vous avez déjà essayé. Et il demande des hypothèses avant la correction.

Contexte : CinéList, Next.js App Router + Supabase. Page /watchlist.
Étapes pour reproduire : 1. je me connecte avec le compte A
2. j'ajoute « Dune » 3. je recharge la page
Attendu : « Dune » apparaît dans ma watchlist.
Obtenu : la liste est vide, aucune erreur dans la console.
Erreur exacte : aucune côté client ; onglet Réseau : 200 avec [].
Dans la table watchlist_items, la ligne existe avec le bon user_id.
Déjà essayé : vider le cache, vérifier la requête.
Action : propose 3 hypothèses classées par probabilité,
avec pour chacune comment la vérifier. Ne modifie aucun fichier pour l'instant.

Éviter la boucle de corrections

La boucle de corrections, c'est quand chaque « corrige ça » de l'IA crée un nouveau problème, et que vous collez l'erreur suivante sans réfléchir. Le code s'alourdit de rustines et plus personne ne sait ce qui a changé.

❌ Boucle

« Toujours pas », « encore une erreur », « corrige », sur dix messages, sans commit intermédiaire ni relecture du diff.

✅ Sortie de boucle

Après deux ou trois tentatives ratées : on s'arrête, on revient au dernier état stable (git restore . ou git stash), on résume ce qu'on sait dans une nouvelle session, et on repart des hypothèses.

Et si le bug est apparu « à un moment » sans qu'on sache quand ?
Si vous avez commité régulièrement, git bisect retrouve le commit fautif par dichotomie : git bisect start, git bisect bad sur la version cassée, git bisect good <commit> sur une version saine, puis vous testez chaque version proposée. C'est une raison de plus de faire de petits commits.

⚙️Les tests automatiques

Un test automatique rejoue une vérification à chaque modification. C'est ce qui vous protège contre la régression : un agent qui corrige une page et en casse une autre sans le dire.

T0npm run build : le test minimal. Il compile le projet et vérifie les types TypeScript. Si le build échoue, Vercel ne déploiera pas.Obligatoire
T1Tests unitaires (Vitest) : vérifient une fonction isolée, rapides, nombreux (validation d'une note, calcul d'un score, formatage).Recommandé
T2Tests end-to-end (Playwright) : pilotent un vrai navigateur et rejouent un parcours complet (connexion, ajout, affichage).Parcours critiques

Un test unitaire avec Vitest

// lib/rating.test.ts
import { describe, it, expect } from 'vitest'
import { isValidRating } from './rating'

describe('isValidRating', () => {
  it('accepte une note entière de 1 à 5', () => {
    expect(isValidRating(4)).toBe(true)
  })
  it('refuse les notes hors bornes', () => {
    expect(isValidRating(0)).toBe(false)
    expect(isValidRating(6)).toBe(false)
  })
})

Installation : npm install -D vitest, puis lancement avec npx vitest (ou un script "test": "vitest" dans package.json).

Un test end-to-end avec Playwright

// e2e/watchlist.spec.ts
import { test, expect } from '@playwright/test'

test('ajouter un film à sa watchlist', async ({ page }) => {
  await page.goto('/login')
  await page.getByLabel('Email').fill('test-a@example.com')
  await page.getByLabel('Mot de passe').fill(process.env.TEST_PASSWORD!)
  await page.getByRole('button', { name: 'Se connecter' }).click()
  await page.goto('/films/dune')
  await page.getByRole('button', { name: 'Ajouter à ma watchlist' }).click()
  await page.goto('/watchlist')
  await expect(page.getByText('Dune')).toBeVisible()
})

Installation : npm init playwright@latest, lancement avec npx playwright test. Les sélecteurs getByLabel et getByRole ont un bonus : ils ne fonctionnent que si vos champs ont de vrais labels, donc ils testent aussi l'accessibilité.

🤖Faire écrire les tests par l'agent… et les vérifier

L'agent écrit des tests très vite. Mais un test qui passe toujours ne prouve rien. Votre travail : vérifier que chaque test échoue quand le code est faux.

🪞 Test tautologique

Le test vérifie ce que le code fait, pas ce qu'il devrait faire. Si le code est faux, le test l'est aussi.

🎭 Tout est simulé

Tout est remplacé par des mocks : le test ne touche plus rien de réel et passe quoi qu'il arrive.

✏️ Test modifié

Pour « faire passer les tests », l'agent modifie l'assertion au lieu de corriger le code. Relisez le diff des fichiers de test.

La vérification par la casse volontaire

1Lancez les tests : ils passent.
2Cassez volontairement le code (par exemple, isValidRating accepte 6).
3Relancez : le test concerné doit échouer, avec un message clair.
4Restaurez le code et vérifiez que tout repasse.
Règle de régressionChaque bug corrigé mérite un test qui l'aurait détecté. Ainsi, le même bug ne peut pas revenir sans que vous le sachiez.

Chapitre 4 sur 6
🔐« Ça marche » n'est pas « c'est sûr »

Un agent optimise pour que la fonctionnalité fonctionne. Si une politique RLS bloque sa requête, il peut proposer de la désactiver ; si une clé manque côté client, il peut proposer d'exposer la clé secrète. Ces raccourcis produisent une application qui marche… pour tout le monde, y compris ceux qui ne devraient rien voir.

Objectif du chapitrePasser une checklist de sécurité sur votre MVP : secrets, droits d'accès, validation des entrées, affichage, dépendances et données personnelles.

Les secrets et variables d'environnement

  • Les valeurs sensibles vivent dans .env.local, qui doit figurer dans .gitignore. En production, elles sont saisies dans les paramètres du projet Vercel.
  • Toute variable préfixée NEXT_PUBLIC_ est intégrée au JavaScript envoyé au navigateur : elle est publique. NEXT_PUBLIC_SUPABASE_URL et NEXT_PUBLIC_SUPABASE_ANON_KEY peuvent l'être, car la clé anon est conçue pour être exposée à condition que RLS protège les tables.
  • SUPABASE_SERVICE_ROLE_KEY contourne toutes les politiques RLS. Elle ne doit jamais être préfixée NEXT_PUBLIC_, jamais importée dans un composant client, et n'est utile que pour des tâches d'administration côté serveur.
⛔ Un secret commité est compromis. Le supprimer dans un nouveau commit ne suffit pas : il reste dans l'historique Git. Il faut régénérer la clé dans le dashboard Supabase, puis mettre à jour .env.local et Vercel.
🛡️Contrôle d'accès : RLS et IDOR

La Row Level Security (RLS) est la vraie barrière de votre application : c'est Postgres qui décide quelles lignes chaque utilisateur peut lire ou modifier, quel que soit le code du front.

-- Activer RLS sur la table
alter table watchlist_items enable row level security;

-- Chaque utilisateur ne lit que ses propres lignes
create policy "Lecture de sa watchlist"
on watchlist_items for select
to authenticated
using ((select auth.uid()) = user_id);

-- Chaque utilisateur n'insère que pour lui-même
create policy "Ajout dans sa watchlist"
on watchlist_items for insert
to authenticated
with check ((select auth.uid()) = user_id);

Il faut une politique par opération nécessaire (select, insert, update, delete). Une table sans RLS activée est lisible par quiconque possède la clé anon, c'est-à-dire tout visiteur.

Le test à deux comptes

1Avec le compte A, créez des données (films notés, jeux, inscriptions).
2Connectez-vous avec le compte B dans une fenêtre de navigation privée.
3Vérifiez que B ne voit rien de A, puis essayez d'ouvrir directement l'URL d'une ressource de A (/watchlist/42).
4Dans l'onglet Réseau, rejouez une requête de modification en changeant l'identifiant : elle doit être refusée.

L'étape 3 teste l'IDOR (Insecure Direct Object Reference) : l'application accepte un identifiant venant de l'utilisateur sans vérifier qu'il lui appartient. C'est une forme de contrôle d'accès cassé, la catégorie de faille la plus fréquente du classement OWASP.

Server Actions = points d'entrée publicsUne Server Action peut être appelée directement, sans passer par votre formulaire. Dans chaque action, récupérez l'utilisateur côté serveur (supabase.auth.getUser()) et ne faites jamais confiance à un user_id envoyé par le client.
🧱Entrées, affichage et dépendances

✅ Validation serveur

Les contrôles du formulaire (required, maxLength) se contournent facilement. Revalidez chaque donnée côté serveur, par exemple avec un schéma Zod : type, longueur, bornes (note entre 1 et 5), format.

💉 Injection

Le client Supabase paramètre les requêtes. Le risque revient quand on construit une chaîne avec une saisie utilisateur : filtre .or() assemblé par concaténation, SQL dynamique dans une fonction Postgres.

🧨 XSS

React échappe le texte affiché par défaut. La protection saute avec dangerouslySetInnerHTML : un avis CinéList contenant du HTML malveillant s'exécuterait chez chaque lecteur. À éviter, ou à assainir (DOMPurify).

📦 Dépendances

npm audit liste les vulnérabilités connues des paquets installés. Avant d'installer un paquet suggéré par l'IA, vérifiez qu'il existe et qu'il est maintenu : npm view nom-du-paquet, page npm, dépôt GitHub.

Le slopsquatting : les paquets hallucinés

Les modèles inventent parfois des noms de paquets plausibles qui n'existent pas. Des attaquants publient ensuite des paquets malveillants sous ces noms, en attendant qu'un développeur lance l'installation suggérée sans vérifier. Un nom inconnu, très récent, avec peu de téléchargements et sans dépôt source est un signal d'alerte.

Données personnelles : le minimum RGPD

  • Ne collectez que ce qui sert au MVP (minimisation) : CampusHub n'a pas besoin de la date de naissance pour une inscription.
  • Permettez à l'utilisateur de supprimer son compte et ses données.
  • N'écrivez pas d'emails ou de mots de passe dans les logs, et ne collez pas de vraies données personnelles dans un prompt : utilisez des données de test.

Chapitre 5 sur 6
✨Un code que vous pourrez encore modifier

Un MVP n'a pas besoin d'être parfait, mais il doit rester modifiable : par vous en S6, par votre binôme, et par l'agent lui-même. Un code incohérent fait produire à l'agent un code encore plus incohérent.

Objectif du chapitreUtiliser les outils de qualité (TypeScript strict, ESLint), refactorer de façon ciblée, vérifier la cohérence avec DESIGN.md et l'accessibilité de base.

TypeScript strict

Avec "strict": true dans tsconfig.json (valeur par défaut de create-next-app), TypeScript refuse les valeurs potentiellement undefined non gérées et les types implicites. C'est un filet de sécurité gratuit. Le piège : l'agent qui « corrige » une erreur de type avec as any ou // @ts-ignore. Il ne corrige rien, il fait taire l'alerte.

Commandes utiles : npx tsc --noEmit vérifie les types sans compiler, npm run build le fait aussi avant de construire.

ESLint : npm run lint

Le linter analyse le code sans l'exécuter : variables inutilisées, dépendances manquantes dans un useEffect, imports en trop, balises img sans alt. Lancez npm run lint avant chaque commit important, et demandez à l'agent de corriger les avertissements un par un en expliquant chaque correction.

Conventions

Les conventions de votre projet (nommage, structure de dossiers, un seul client Supabase dans lib/, Server Actions dans actions.ts) sont écrites dans AGENTS.md depuis la S3. Si l'agent ne les respecte pas, corrigez le code et précisez AGENTS.md pour que l'erreur ne se reproduise pas.

🔧Refactoring ciblé et dette technique

Refactorer, c'est améliorer la structure du code sans changer son comportement. Avec un agent, le danger est le « grand nettoyage » qui touche trente fichiers et casse ce qui marchait.

❌ Refactoring global

« Nettoie tout le projet et améliore le code. » Diff illisible, comportements modifiés, impossible à relire.

✅ Refactoring ciblé

« Les pages /watchlist et /favoris dupliquent la même requête. Extrais-la dans lib/queries.ts sans changer le comportement, puis lance npm run build. »

Un refactoring ciblé se fait sur une branche ou après un commit propre, avec les tests et la recette relancés ensuite pour prouver que rien n'a changé.

La dette technique

La dette technique, ce sont les raccourcis pris aujourd'hui qui coûteront du temps demain : doublons, contournements, absence de tests, données simulées. En accumuler un peu est normal pour un MVP ; l'important est de la connaître. Listez-la dans AI-LOG.md ou dans le README (« connu, non traité ») : c'est un signe de maturité, pas un aveu de faiblesse.

🎨Cohérence visuelle, responsive et accessibilité

L'UX/UI fait partie de l'évaluation. Or l'agent a tendance à inventer une couleur, une marge ou un bouton à chaque nouvelle page.

Cohérence avec DESIGN.md

  • Les couleurs, typographies et espacements utilisés sont-ils ceux de DESIGN.md, ou des valeurs en dur apparues au fil des générations ?
  • Les composants (boutons, cartes, champs) sont-ils réutilisés, ou recréés page par page ?
  • Le responsive tient-il sur un écran mobile ? Testez avec le mode appareil des DevTools, pas seulement en réduisant la fenêtre.

Accessibilité : le minimum à vérifier

🏷️ Labels

Chaque champ de formulaire a un <label> associé. Un placeholder ne remplace pas un label.

🌓 Contraste

Le texte courant doit atteindre un rapport de contraste d'au moins 4.5:1 avec son fond (WCAG niveau AA).

⌨️ Clavier

Toute l'application se parcourt avec Tab, Entrée et Échap, avec un focus visible. Une div cliquable n'est pas un bouton.

🖼️ Texte alternatif

Chaque affiche de film ou jaquette de jeu a un alt descriptif ; une image décorative a un alt vide.

Outil rapideL'audit Lighthouse (onglet Lighthouse des DevTools de Chrome) donne un premier score d'accessibilité et de bonnes pratiques. Il ne remplace pas un test au clavier, mais il repère vite les oublis.

👀Relire un diff comme un reviewer

En entreprise, aucun code n'entre dans la branche principale sans revue. En vibe coding, c'est encore plus vrai : l'auteur est une IA et le seul humain dans la boucle, c'est vous.

Objectif du chapitreRelire un diff avec une checklist, obtenir un second avis critique d'une autre session d'IA, classer les problèmes par sévérité et tracer la décision dans AI-LOG.md.

🤝Le second avis : une IA en reviewer critique

L'agent qui a écrit le code est mal placé pour le critiquer : il a le même contexte et les mêmes angles morts. Ouvrez une nouvelle session (ou un autre outil) et donnez-lui un rôle explicite de reviewer exigeant.

Contexte : projet GameBacklog, Next.js App Router + Supabase (RLS).
Voici le diff de la fonctionnalité « changer le statut d'un jeu » (git diff main).
Rôle : tu es un reviewer senior exigeant, spécialisé sécurité et qualité.
Tu n'as pas écrit ce code et tu ne dois pas le défendre.
Action : liste les problèmes trouvés.
Contraintes : pour chaque problème, indique le fichier et la ligne,
la sévérité (bloquant / majeur / mineur / suggestion), le risque concret
et une correction proposée. Ne réécris pas tout le fichier.
Si tu n'es pas sûr, dis-le au lieu d'inventer.
Format : tableau trié par sévérité décroissante.

Classer par sévérité

S1Bloquant : faille de sécurité, perte ou fuite de données, build cassé. On ne fusionne pas.Stop
S2Majeur : fonctionnalité incorrecte, critère d'acceptation non respecté, erreur non gérée.À corriger
S3Mineur : doublon, nommage, incohérence visuelle, avertissement de lint.Si possible
S4Suggestion : amélioration possible, hors périmètre du MVP.Plus tard
⛔ Un reviewer IA se trompe aussi. Il peut signaler un faux problème ou en inventer. Chaque remarque se vérifie dans le code avant d'être corrigée.
📝Décider et tracer

Pour chaque remarque, trois décisions possibles, toujours justifiées.

✅ Accepter

Le code est correct et compris : on commite avec un message explicite.

🔧 Corriger

Le problème est réel : on corrige (soi-même ou via l'agent), on revérifie, on commite séparément.

🗑️ Rejeter

Le code est hors périmètre, trop complexe ou incompris : on annule et on reformule la demande.
