🎯Mettre en pratique la séance 5

Ce support vous fait manipuler les notions du support théorique, puis les appliquer à votre projet fil rouge.

À la fin de cette séance, vous serez capable de :
  • Lire et comprendre un code généré en suivant le chemin des données ;
  • Déboguer méthodiquement avec l'IA à partir d'une erreur exacte et reproductible ;
  • Tester le MVP par une recette manuelle, des tests unitaires et des tests end-to-end ;
  • Vérifier la sécurité d'une application Next.js / Supabase générée (secrets, RLS, validation, XSS, dépendances) ;
  • Améliorer la qualité et la maintenabilité du code (TypeScript strict, lint, accessibilité, DESIGN.md) ;
  • Conduire une revue de code assistée par IA et tracer les décisions dans AI-LOG.md.

Prompt de départ

Contexte : je développe [CinéList / GameBacklog / CampusHub], un MVP Next.js (App Router, TypeScript) + Supabase (Auth, Postgres, RLS), déployé sur Vercel. Les fichiers PROJECT.md, DESIGN.md, AGENTS.md et AI-LOG.md décrivent le projet.

Rôle : tu es un testeur QA et un reviewer sécurité exigeant. Tu n'as pas écrit ce code et tu ne dois pas le défendre.

Objectif / Action :
1. À partir des critères d'acceptation de PROJECT.md, propose une liste de scénarios de recette, avec pour chacun les étapes et le résultat attendu, en ajoutant les cas limites pertinents.
2. Passe en revue le code pour la checklist sécurité : variables d'environnement et clé service_role, RLS activée et politiques de chaque table, vérification de l'utilisateur dans chaque Server Action, validation serveur, dangerouslySetInnerHTML, dépendances de package.json.
3. Pour chaque problème, indique le fichier, la sévérité (bloquant / majeur / mineur / suggestion) et une correction proposée.

Contraintes : ne modifie aucun fichier. Ne propose aucune nouvelle dépendance sans vérifier qu'elle existe. Si tu n'es pas sûr, dis-le au lieu d'inventer.

# Rapport de bug — Un utilisateur voit la watchlist d'un autre compte

## Étapes pour reproduire
- Se connecter avec le compte A (test-a@example.com)
- Ajouter « Dune » et « Arcane » à sa watchlist
- Se déconnecter, puis se connecter avec le compte B (test-b@example.com) dans une fenêtre privée
- Ouvrir /watchlist

## Résultat attendu
Le compte B voit une watchlist vide (il n'a encore rien ajouté).

## Résultat obtenu
Le compte B voit « Dune » et « Arcane », les films du compte A.

## Erreur exacte
Aucune erreur dans la console du navigateur ni dans le terminal.
Onglet Réseau : GET /rest/v1/watchlist_items?select=* renvoie 200 avec les lignes des deux comptes.
Dashboard Supabase : la table watchlist_items est signalée « RLS disabled ».

## Environnement
Production Vercel (https://cinelist.vercel.app), Chrome, commit a1b2c3d. Reproduit aussi en local.

## Hypothèses (classées)
- RLS non activée sur la table watchlist_items (confirmée dans le dashboard)
- Requête de la page sans filtre sur l'utilisateur connecté (confirmée : select * sans condition)
- Mauvais client Supabase utilisé (clé service_role) : écartée, le client utilise bien la clé anon

## Correction
Migration SQL :
- alter table watchlist_items enable row level security;
- politique select : using ((select auth.uid()) = user_id)
- politique insert : with check ((select auth.uid()) = user_id)
- politique delete : using ((select auth.uid()) = user_id)
Server Action addToWatchlist : le user_id est désormais lu via supabase.auth.getUser() côté serveur au lieu d'être envoyé par le formulaire.
Commit : fix(watchlist): activer RLS et lire l'utilisateur côté serveur

## Vérification
- Test à 2 comptes : B ne voit plus les films de A
- Accès direct à /watchlist/42 (item de A) depuis B : aucune donnée renvoyée
- Insertion rejouée depuis l'onglet Réseau avec le user_id de A : refusée (new row violates row-level security policy)
- Parcours normal de A inchangé : ajout, affichage et suppression OK
- npm run build OK, npm run lint OK
- Entrée ajoutée dans AI-LOG.md (bug bloquant, hypothèses, correction, vérification)
