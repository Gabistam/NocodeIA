Chapitre 1 sur 6
🐙Un repository GitHub propre

Votre repository est la première chose que le jury ouvre. Avant même de lancer l'application, il lit la structure, le README, l'historique des commits. Un repository propre prouve que vous maîtrisez ce que l'agent a produit.

Objectif du chapitreOrganiser un repository lisible et sûr : structure claire, fichiers sensibles exclus, commits explicites, branches et pull requests, et savoir réagir si un secret a fuité.

Ce que doit contenir un repository de MVP

cinelist/
├── app/                  # routes Next.js (App Router)
├── components/           # composants UI réutilisables
├── lib/                  # clients Supabase, utilitaires
├── supabase/migrations/  # schéma SQL versionné
├── public/
├── .env.example          # noms des variables, sans valeurs
├── .gitignore            # exclut .env.local, node_modules, .next
├── PROJECT.md  DESIGN.md  AGENTS.md
├── README.md             # porte d'entrée du projet
├── AI-LOG.md             # journal des décisions IA
├── package.json  package-lock.json
└── tsconfig.json

❌ À éviter

Un dossier test2-final, des fichiers old_page.tsx jamais supprimés, un .env.local commité, des captures d'écran en vrac à la racine, un README généré par défaut par create-next-app.

✅ À faire

Une arborescence que l'on comprend sans explication, du code mort supprimé, les fichiers de contexte (PROJECT.md, AGENTS.md…) à la racine, un README réécrit pour votre projet.

🙈.gitignore et .env.example

Le fichier .gitignore liste ce que Git ne doit jamais suivre : dépendances (node_modules/), build (.next/), et surtout vos fichiers de secrets (.env.local). Le .gitignore généré par npx create-next-app@latest ignore déjà les fichiers .env*.

Le fichier .env.example fait l'inverse : il est commité et documente les variables nécessaires, sans leurs valeurs. Comme le .gitignore ignore .env*, ajoutez l'exception !.env.example pour qu'il soit suivi.

# .env.example — copier en .env.local puis remplir
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
# serveur uniquement, jamais préfixée NEXT_PUBLIC_
SUPABASE_SERVICE_ROLE_KEY=
Règle NEXT_PUBLIC_Toute variable préfixée NEXT_PUBLIC_ est intégrée au JavaScript envoyé au navigateur : elle est publique. La clé anon de Supabase peut l'être car la RLS protège les données. La clé SUPABASE_SERVICE_ROLE_KEY contourne la RLS : elle reste côté serveur, sans préfixe, et n'apparaît jamais dans un composant client.

Si un fichier sensible a déjà été suivi, l'ajouter au .gitignore ne suffit pas : retirez-le de l'index avec git rm --cached .env.local, puis commitez. Il reste cependant présent dans l'historique (voir plus bas).

📝Commits, branches et pull requests

Un historique lisible raconte la construction du projet. La convention Conventional Commits préfixe chaque message par un type : feat (fonctionnalité), fix (correction), docs (documentation), refactor, style, test, chore (maintenance), avec une portée optionnelle entre parenthèses.

Message flouMessage clair
updatefeat(watchlist): ajouter le filtre par statut vu / à voir
fix bugfix(auth): rediriger vers /dashboard après confirmation email
modifs claudedocs: compléter le README avec les comptes de test
wip wip wiprefactor(events): extraire la carte événement en composant

Travailler par branche

1Créer une branche de fonctionnalité depuis main : git switch -c feat/recherche-jeux.
2Faire travailler l'agent, relire, puis git add et git commit -m "feat(games): rechercher un jeu par titre".
3Pousser la branche : git push -u origin feat/recherche-jeux.
4Ouvrir une pull request sur GitHub : description, captures, relecture (par votre binôme ou par vous-même avec l'aide de l'IA).
5Fusionner dans main seulement quand le build passe et la preview fonctionne.

Même seul, la pull request est utile : elle regroupe un changement cohérent, déclenche un déploiement de preview sur Vercel et laisse une trace lisible pour le jury. Consultez votre historique avec git log --oneline.

🔑Aucun secret dans l'historique

Git conserve tout. Un secret supprimé dans le dernier commit reste lisible dans les commits précédents, et un repository public est parcouru en permanence par des robots qui cherchent des clés.

⛔ Un secret a fuité ? Le réflexe n'est pas de réécrire l'historique en premier, mais de considérer la clé comme compromise.
1Révoquer / régénérer la clé chez le fournisseur (Supabase, OpenAI, TMDB…) : c'est la rotation de secret. L'ancienne clé devient inutilisable.
2Mettre à jour la nouvelle valeur dans .env.local et dans les variables d'environnement Vercel, puis redéployer.
3Nettoyer l'historique si nécessaire (outils comme git filter-repo ou BFG Repo-Cleaner) et vérifier les logs d'usage du fournisseur.
4Prévenir la récidive : .gitignore correct, protection contre les push de secrets de GitHub (secret scanning / push protection) activée, consigne dans AGENTS.md.
Rotation d'abord, nettoyage ensuite.

Nettoyer l'historique ne rend pas un secret à nouveau secret : quelqu'un a pu le copier avant. Seule la révocation le neutralise.

Chapitre 2 sur 6
▲De GitHub à une URL publique

Vercel est la plateforme de référence pour Next.js : elle se connecte à votre repository GitHub, construit l'application à chaque push et la publie sur une URL publique en HTTPS.

git push→GitHub→Build Vercel→Déploiement→URL publique

Premier déploiement

1Vérifier en local que npm run build passe sans erreur : si le build échoue chez vous, il échouera sur Vercel.
2Sur Vercel : Add New… → Project, puis importer le repository GitHub (autoriser l'accès si demandé).
3Vercel détecte le framework Next.js et propose la commande de build ; laissez les valeurs par défaut sauf besoin précis.
4Renseigner les variables d'environnement (NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, éventuellement SUPABASE_SERVICE_ROLE_KEY).
5Lancer le déploiement, ouvrir l'URL https://cinelist-xxx.vercel.app et tester le parcours complet.
🌿Preview et production

Une fois le repository relié, Vercel fait du déploiement continu : chaque push déclenche un nouveau build.

🔍 Déploiement de preview

Créé pour chaque push sur une autre branche que main et pour chaque pull request. Il a sa propre URL, commentée automatiquement dans la PR. Idéal pour tester feat/inscriptions de CampusHub sans toucher au site public.

🚀 Déploiement de production

Créé à chaque push (ou fusion) sur la branche de production, main par défaut. Il met à jour l'URL principale du projet, celle que vous donnez au jury.

Variables par environnement

Chaque variable peut être définie pour Production, Preview et Development. Vous pouvez ainsi pointer vos previews vers un projet Supabase de test et la production vers le projet réel. La commande vercel env pull du CLI Vercel récupère les variables de développement dans un fichier local.

⛔ Piège classique Modifier une variable sur Vercel ne change pas le déploiement déjà en ligne. Il faut redéployer. Les variables NEXT_PUBLIC_ sont en plus intégrées au moment du build : sans nouveau build, l'ancienne valeur reste dans le JavaScript servi.
🌐URL publique et domaines

Vercel attribue une URL publique en .vercel.app à la production, plus une URL unique par déploiement. Vous pouvez ajouter un domaine personnalisé (gamebacklog.fr) dans les réglages du projet, en configurant les enregistrements DNS indiqués par Vercel.

  • Pour la soutenance, l'URL .vercel.app de production suffit : notez-la dans le README et dans la description du repository GitHub.
  • Toute nouvelle URL (domaine personnalisé, previews) doit être déclarée dans l'authentification Supabase, sinon les redirections échouent (chapitre suivant).
  • Vérifiez la visibilité : les previews peuvent être protégées par l'authentification Vercel (Deployment Protection) ; la production doit rester accessible au jury.
main = production.

Ne poussez sur main que ce qui a été testé en preview. Tout ce qui arrive sur main part en ligne.

Chapitre 3 sur 6
🔐L'authentification en production

En local, Supabase renvoie vos utilisateurs vers http://localhost:3000. En ligne, c'est la première chose qui casse : liens de confirmation qui ouvrent localhost, connexion qui boucle, redirection refusée.

Dans le tableau de bord Supabase, section Authentication → URL Configuration :

🏠 Site URL

L'URL par défaut de votre application, utilisée dans les emails (confirmation, réinitialisation) quand aucune redirection n'est précisée. En production : https://cinelist.vercel.app.

↪️ Redirect URLs

La liste autorisée des URLs vers lesquelles l'auth peut renvoyer : https://cinelist.vercel.app/auth/callback, http://localhost:3000/**, et un motif pour les previews Vercel. Une URL absente est refusée.

Confirmations email

Par défaut, Supabase exige que l'utilisateur confirme son adresse avant de se connecter. Vérifiez en production que l'email arrive, que le lien pointe vers votre domaine Vercel et que la route de callback échange bien le code contre une session. Le service d'email intégré de Supabase est limité en volume et destiné aux tests : pour un usage réel, configurez un SMTP personnalisé.

Pour la soutenanceCréez à l'avance des comptes de test déjà confirmés. Le jury ne doit pas attendre un email pour tester CampusHub.
🗄️Base de données : migrations et RLS

Une migration est un fichier SQL versionné (dans supabase/migrations/) qui décrit une évolution du schéma. Elle permet de reproduire exactement la même base ailleurs et de savoir ce qui a été appliqué.

  • Avec le CLI Supabase : supabase migration new add_reviews crée le fichier, supabase link relie le projet distant, supabase db push applique les migrations en attente.
  • Si vous avez tout fait dans le SQL Editor, exportez au moins le SQL final dans le repository : c'est la preuve de votre modèle de données.
  • Vérifiez que la production contient bien toutes les tables : une table favorites créée seulement en local fera planter la page en ligne.
⛔ RLS en production Contrôlez à nouveau que la RLS est activée sur chaque table exposée et que les policies filtrent par auth.uid(). Le Security Advisor du tableau de bord Supabase signale les tables sans RLS. Testez avec deux comptes : l'utilisateur A ne doit jamais voir la watchlist de B.
📜Lire les logs

Quand ça marche en local mais pas en ligne, ne demandez pas « corrige » à l'agent à l'aveugle : allez chercher le message d'erreur réel dans les logs.

OùCe qu'on y trouve
Vercel → Deployments → Build LogsErreurs de compilation : TypeScript, import introuvable, dépendance manquante.
Vercel → Logs (runtime)Erreurs à l'exécution des Server Components, Server Actions et Route Handlers.
Supabase → LogsRequêtes API refusées, erreurs Postgres, événements d'authentification.
Console du navigateurErreurs côté client, requêtes réseau en échec (onglet Réseau).

Copiez l'erreur exacte dans votre prompt : contexte (production Vercel), message, fichier concerné, ce que vous avez déjà vérifié.

🧯Les erreurs de déploiement courantes
SymptômeCause probableCorrection
« supabaseUrl is required » ou page blancheVariable d'environnement manquante ou mal nommée sur VercelAjouter la variable pour le bon environnement, puis redéployer
Build en échec, « Type error »Erreur TypeScript tolérée par npm run dev ; selon la version et la configuration, erreur de lintLancer npm run build et npm run lint en local, corriger, repousser
Lien de confirmation qui ouvre localhostSite URL restée sur http://localhost:3000Mettre l'URL Vercel dans Site URL et Redirect URLs
« Module not found: ./components/Header »Fichier nommé header.tsx : macOS et Windows ignorent la casse, le serveur Linux de Vercel nonAligner l'import et le nom du fichier (git mv pour renommer)
Liste vide en ligne, pleine en localTable ou policy RLS absente en productionAppliquer les migrations, vérifier les policies

La sensibilité à la casse est un piège sournois : renommer seulement la casse d'un fichier peut ne pas être détecté par Git sur macOS ou Windows. git mv header.tsx Header.tsx enregistre le changement correctement.

Chapitre 4 sur 6
📖README.md : la porte d'entrée

Le README.md répond en une lecture à trois questions : qu'est-ce que c'est, est-ce que ça marche, comment je le lance. C'est le document que le jury, un recruteur ou un futur coéquipier lit en premier.

🎯 Pitch

Une ou deux phrases : pour qui, quel problème, quelle solution.

✅ Fonctionnalités

Ce qui marche réellement dans le MVP, pas la liste des envies.

🧱 Stack

Next.js / TypeScript, Supabase, Vercel, agent utilisé.

⚙️ Installation

Clonage, npm install, copie du .env.example, npm run dev.

🔧 Variables d'env.

Nom, rôle, public ou serveur. Jamais les valeurs.

🌐 Démo

URL publique, comptes de test, captures d'écran.

Le guide d'installation doit être testé : clonez votre repository dans un nouveau dossier et suivez vos propres instructions à la lettre. Si vous devez improviser une étape, elle manque au README.

🤖AI-LOG.md et PROJECT.md à jour

Le AI-LOG.md est la preuve de votre méthodologie IA. Finalisé, il doit montrer que vous avez piloté l'agent, pas subi ses propositions.

## Décision — Recherche des événements (CampusHub)
- Contexte : filtre par date et par campus demandé en S4
- Prompt / agent : Claude Code, plan demandé avant exécution
- Proposition IA : filtrer côté client après chargement complet
- Décision : refusé, filtrage côté Supabase (.eq, .gte) pour la pagination
- Vérification : test avec 2 comptes, build OK, RLS inchangée

Le PROJECT.md doit décrire l'état réel à la livraison : fonctionnalités livrées, fonctionnalités reportées, décisions de périmètre. Un PROJECT.md qui promet encore des notifications jamais construites décrédibilise le reste.

❌ AI-LOG vide de sens

« J'ai demandé à Claude de faire la page, ça marche. »

✅ AI-LOG utile

Ce qui a été demandé, ce que l'IA a proposé, ce que vous avez accepté ou refusé, et comment vous l'avez vérifié.

🔎Faire rédiger par l'IA, puis vérifier

L'agent connaît votre code : il rédige vite un premier jet de README à partir du package.json, de l'arborescence et de vos fichiers de contexte. Mais il invente facilement.

1Donner le contexte : PROJECT.md, AI-LOG.md, .env.example, URL de production.
2Imposer une structure et une contrainte : « uniquement ce qui existe dans le code, signale ce que tu ne peux pas vérifier ».
3Pratiquer la relecture humaine ligne par ligne : chaque fonctionnalité citée existe-t-elle ? chaque commande fonctionne-t-elle ?
4Tester le guide d'installation et l'URL de démo, puis commiter : docs: rédiger le README.
⛔ Hallucinations de documentation Fonctionnalité annoncée mais absente, commande npm run seed qui n'existe pas dans le package.json, badge de tests alors qu'il n'y a pas de tests, vraie clé recopiée depuis .env.local : autant d'erreurs que le jury repère immédiatement.

🎤Construire le plan de soutenance

La soutenance n'est pas une visite guidée de toutes les pages. C'est une démonstration qui prouve trois choses : le produit répond à un besoin, il fonctionne, et vous savez comment il a été construit.

1

Pitch

Le problème, la cible, la solution, en quelques phrases.

« Pourquoi cette appli ? »
2

Démo

Un parcours utilisateur réaliste, de bout en bout, en production.

« Est-ce que ça marche ? »
3

Choix techniques

Modèle de données, auth, RLS, déploiement.

« Pourquoi comme ça ? »
4

Méthode IA

Contexte, pilotage, contrôle : fichiers, extraits d'AI-LOG.

« Qui a décidé ? »
5

Limites et suite

Ce qui ne marche pas encore, pourquoi, et la prochaine étape.

« Et après ? »
🎬La démo scénarisée

Une démo scénarisée suit un parcours écrit à l'avance, avec des données préparées. Exemple pour GameBacklog :

1Connexion avec le compte de test demo@gamebacklog.dev (backlog déjà rempli de quelques jeux).
2Ajout d'un jeu, passage de « à jouer » à « en cours » (CRUD + relation utilisateur / jeu).
3Recherche par titre et filtre par statut.
4Dashboard personnel, puis affichage mobile (responsive).
5Connexion avec un second compte : le backlog du premier est invisible (RLS).
Le plan BLe wifi tombe, Supabase répond lentement, un déploiement fait au dernier moment casse tout. Préparez un plan B de démo : vidéo enregistrée du parcours, captures d'écran, déploiement précédent prêt à être restauré (rollback Vercel), application lancée en local. Et ne poussez rien sur main juste avant de passer.
🧠Montrer la méthode IA et défendre ses choix

Le jury évalue la méthodologie IA : montrez le chemin Prompt → Context → Agentic sur des exemples concrets.

  • Contexte : ouvrez PROJECT.md, DESIGN.md, AGENTS.md et expliquez ce qu'ils ont changé dans les réponses de l'agent.
  • Pilotage : un plan demandé avant exécution, une tâche découpée, un niveau de délégation choisi.
  • Contrôle : une proposition refusée, un bug détecté en relecture, une policy RLS corrigée (extrait d'AI-LOG).

Répondre aux questions du jury

Question probableRéponse attendue
« Pourquoi Supabase ? »Postgres relationnel, Auth intégrée, RLS pour isoler les données de chaque utilisateur.
« Expliquez cette policy. »Lire la policy et dire en français qui peut faire quoi, sur quelle table.
« Qu'avez-vous écrit vous-même ? »Les fichiers de contexte, les décisions, les corrections : l'AI-LOG sert de preuve.
« Que se passe-t-il si… ? »Être honnête : « ce cas n'est pas géré, voici comment je le traiterais ».
🚧Assumer ce qui ne marche pas encore

Présenter ses limites connues est un signe de maîtrise, pas un aveu d'échec. Pour chaque limite : ce qui manque, pourquoi (priorité, temps, complexité, risque), et comment vous le feriez.

❌ À éviter

Cacher un bug en espérant que le jury ne clique pas au mauvais endroit, ou répondre « c'est l'IA qui a fait ça » à une question sur le code.

✅ À faire

« La recherche de CinéList ne gère pas encore les accents. J'ai priorisé la RLS. La correction passerait par une recherche insensible aux accents côté Postgres. »

Vous défendez un produit et une méthode.

Le jury ne cherche pas une application parfaite, mais quelqu'un qui comprend, contrôle et assume ce qu'il livre.

Chapitre 6 sur 6
➕Les bonus, une fois le MVP solide

Les bonus valorisent un projet qui fonctionne déjà. Un bonus brillant sur un socle cassé (auth instable, CRUD incomplet, RLS absente) ne compense rien.

🤖 API IA

Résumé des avis de CinéList, suggestion de jeux pour GameBacklog. Appel depuis un Route Handler (app/api/.../route.ts) ou une Server Action.

🎞️ API externe

TMDB pour les affiches et synopsis de films, RAWG pour les jaquettes et plateformes de jeux. Clé obtenue sur le site du fournisseur.

⚡ Automatisation

n8n ou Make : email de rappel la veille d'un événement CampusHub, déclenché par un webhook ou une planification.

⛔ Clé API côté serveur uniquement Une clé OpenAI, Anthropic, TMDB ou RAWG ne se préfixe jamais par NEXT_PUBLIC_. Le navigateur appelle votre route serveur, qui appelle le fournisseur avec la clé API côté serveur lue dans process.env. Ajoutez-la dans Vercel et dans .env.example (sans valeur).
// app/api/movies/search/route.ts (principe)
export async function GET(request: Request) {
  const query = new URL(request.url).searchParams.get('q')
  // la clé reste sur le serveur
  const res = await fetch(`https://api.themoviedb.org/3/search/movie?query=${encodeURIComponent(query ?? '')}`, {
    headers: { Authorization: `Bearer ${process.env.TMDB_API_TOKEN}` },
  })
  return Response.json(await res.json())
}
🔁Itérer après le MVP

Le MVP est un point de départ. L'itération post-MVP part des retours réels : jury, camarades, premiers utilisateurs.

1Collecter les retours (questions du jury, tests par des camarades, bugs constatés).
2Les trier : bug, amélioration UX, nouvelle fonctionnalité. Les bugs passent d'abord.
3Mettre à jour PROJECT.md (nouveau périmètre), puis ouvrir des issues GitHub.
4Reprendre le cycle : contexte → plan de l'agent → branche → PR → preview → production.
⚖️Livrer de manière responsable

💶 Coûts

Les offres gratuites de Vercel et Supabase ont des quotas ; une API IA est facturée à l'usage. Fixez une limite de dépenses et protégez vos routes pour éviter qu'un robot ne vide votre crédit.

🔒 Données personnelles

Emails, avis, inscriptions sont des données personnelles (RGPD) : collectez le minimum, ne les envoyez pas à une API IA sans raison, permettez la suppression du compte.

🔗 Dépendance fournisseur

Vercel, Supabase, un modèle IA : chaque service peut changer ses prix ou ses conditions. Savoir ce qui serait difficile à migrer fait partie des choix techniques.

🧭 Limites du vibe coding

Aller vite ne dispense pas de comprendre. Un code que vous ne savez pas expliquer, maintenir ou sécuriser n'est pas vraiment le vôtre.

🔑Le message clé
Un MVP n'existe vraiment que lorsqu'il est en ligne, compréhensible par quelqu'un d'autre et défendu par celui qui l'a construit : l'IA vous aide à livrer, mais c'est vous qui répondez de ce qui est livré.
À la fin de cette séance, vous serez capable de :
  • Organiser un repository GitHub propre : structure, .gitignore, .env.example, commits et historique lisibles ;
  • Réagir correctement à la fuite d'un secret : révoquer, régénérer, puis nettoyer ;
  • Déployer une application Next.js sur Vercel avec les bonnes variables d'environnement ;
  • Configurer Supabase pour la production : URL d'authentification, migrations, RLS et logs ;
  • Diagnostiquer les erreurs de déploiement les plus courantes ;
  • Rédiger avec l'IA puis vérifier un README.md, un AI-LOG.md et un PROJECT.md à jour ;
  • Préparer et défendre une soutenance qui montre le produit et la méthode IA.
