Chapitre 1 sur 6
🧱Deux mondes : le serveur et le navigateur

Une application Next.js (App Router) s'exécute à deux endroits : sur le serveur (chez Vercel) et dans le navigateur de l'utilisateur. Savoir ce qui tourne où, c'est savoir ce qui est sûr, ce qui est rapide et ce que l'agent doit générer.

Objectif du chapitreComprendre la répartition client / serveur dans Next.js, choisir entre Server Component, Client Component, Server Action et route handler, et brancher Supabase proprement avec @supabase/ssr et les variables d'environnement.

Server Components et Client Components

Dans l'App Router, tout composant est un Server Component par défaut. Il s'exécute sur le serveur, peut lire la base directement, n'envoie aucun JavaScript au navigateur pour lui-même, mais ne peut pas utiliser useState, useEffect ni d'événements comme onClick. Dès qu'un fichier commence par la directive 'use client', il devient un Client Component : il est hydraté dans le navigateur et devient interactif.

Server Component ArchitectureClient Component
Où il s'exécuteServeur uniquementRendu serveur puis navigateur (hydratation)
Accès aux donnéesDirect : client Supabase serveur, cookies, variables secrètesVia le client Supabase navigateur (clé publique) ou via une Server Action
InteractivitéAucune (pas de state, pas d'événements)useState, onClick, formulaires contrôlés, animations
Exemple CinéListLa page « Ma watchlist » qui charge les films de l'utilisateurLe composant de notation par étoiles cliquables
Règle pratiqueGardez les pages et les listes en Server Components, et descendez 'use client' le plus bas possible dans l'arbre : seulement sur les petits composants qui ont besoin d'interactivité (bouton favori, modale de confirmation, champ de recherche en direct).
⚙️Où vit la logique métier ?

Créer un avis, inscrire un étudiant à un événement, changer le statut d'un jeu : ces actions modifient la base. Elles doivent s'exécuter sur le serveur, jamais uniquement dans le navigateur.

📝 Server Action

Fonction asynchrone marquée 'use server', appelée directement depuis un formulaire (<form action={addReview}>). Idéale pour les mutations de vos propres écrans : ajouter à la watchlist, supprimer une inscription CampusHub.

🔌 Route handler

Fichier app/api/.../route.ts qui exporte GET, POST… Utile pour une vraie API HTTP : webhook, callback d'authentification (app/auth/callback/route.ts), appel depuis un service externe.

📄 Server Component

Lecture des données pour l'affichage : la page /backlog de GameBacklog lit les entrées de l'utilisateur au moment du rendu, sans appel fetch côté navigateur.

🖱️ Client Component

Interaction et retour visuel immédiat : état « en cours d'envoi », ouverture d'une modale, tri visuel. Il délègue les écritures à une Server Action.

Brancher Supabase avec @supabase/ssr

Le paquet @supabase/ssr fournit deux fabriques : createBrowserClient pour les Client Components et createServerClient pour le serveur (Server Components, Server Actions, route handlers, middleware). Le client serveur lit et écrit la session dans les cookies, ce qui permet au serveur de savoir qui est connecté. On range ces deux clients dans lib/supabase/client.ts et lib/supabase/server.ts.

// lib/supabase/server.ts
import { createServerClient } from '@supabase/ssr'
import { cookies } from 'next/headers'

export async function createClient() {
  const cookieStore = await cookies()
  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() { return cookieStore.getAll() },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) =>
              cookieStore.set(name, value, options))
          } catch {
            // appelé depuis un Server Component : le middleware rafraîchit la session
          }
        },
      },
    }
  )
}
⛔ Piège fréquent L'ancien paquet @supabase/auth-helpers-nextjs est déprécié. Si l'agent le propose, refusez et demandez explicitement @supabase/ssr : notez-le dans AGENTS.md pour que la consigne soit permanente.
🔑Variables d'environnement et structure du repo

Les adresses et clés de Supabase ne s'écrivent jamais en dur dans le code : elles vivent dans des variables d'environnement, différentes en local et en production.

  • NEXT_PUBLIC_SUPABASE_URL et NEXT_PUBLIC_SUPABASE_ANON_KEY : le préfixe NEXT_PUBLIC_ les rend lisibles dans le navigateur. C'est voulu : elles sont publiques par conception, la sécurité repose sur RLS.
  • SUPABASE_SERVICE_ROLE_KEY : sans préfixe, donc accessible uniquement côté serveur. Elle contourne RLS : à n'utiliser que pour des tâches d'administration, jamais dans un Client Component.
  • En local, elles vont dans .env.local (ignoré par Git) ; en production, dans les paramètres Environment Variables du projet Vercel.
app/
  (auth)/login/page.tsx        // formulaire de connexion
  auth/callback/route.ts       // route handler : retour du magic link
  dashboard/page.tsx           // Server Component protégé
  films/[id]/page.tsx
  films/actions.ts             // Server Actions ('use server')
lib/supabase/client.ts         // createBrowserClient
lib/supabase/server.ts         // createServerClient
supabase/migrations/           // fichiers SQL versionnés
middleware.ts                  // rafraîchit la session (proxy.ts depuis Next.js 16)
.env.local                     // jamais commité
Lire côté serveur, interagir côté client, écrire via une Server Action.

Donnez cette règle à votre agent dans AGENTS.md : elle suffit à éviter la plupart des architectures bancales générées par l'IA.

Chapitre 2 sur 6
🗂️Entités, attributs et types

Avant la moindre ligne de code, il faut savoir quelles « choses » votre application manipule et comment elles sont reliées. Un schéma de données bancal se paie à chaque écran : c'est le ticket le plus important de la séance.

  • Entité : un type d'objet métier qui devient une table (un film, un jeu, un événement, une inscription).
  • Attribut : une propriété de l'entité, qui devient une colonne (title, status, rating).
  • Type : la nature de la valeur en Postgres : text, integer, boolean, timestamptz, uuid, date.
  • Contraintes : not null, unique, check (rating between 1 and 5), default now(). Elles protègent la cohérence même si le front se trompe.

Clé primaire et clé étrangère

Chaque ligne a un identifiant unique : la clé primaire. Avec Supabase, on utilise un uuid généré par gen_random_uuid() : impossible à deviner, contrairement à un entier auto-incrémenté (/films/3 laisse imaginer /films/4). Une clé étrangère est une colonne qui référence la clé primaire d'une autre table (references public.films(id)) : Postgres refuse alors une valeur qui n'existe pas.

🔗Relations 1-N et N-N

1️⃣ Relation 1-N

Un élément est lié à plusieurs autres, chacun d'eux ne pointant que vers un seul. Un organisateur CampusHub crée plusieurs événements : events.organizer_id référence profiles.id. La clé étrangère se place toujours du côté « plusieurs ».

🔀 Relation N-N

Un étudiant s'inscrit à plusieurs événements et un événement accueille plusieurs étudiants. On crée une table de jointure registrations(user_id, event_id) avec une contrainte unique (user_id, event_id) pour interdire les doublons.

ProjetEntitésRelations clés
🎬 CinéListprofiles, films, watchlist_items, reviewswatchlist_items = jointure N-N profils ↔ films (statut, favori) ; reviews = un avis par utilisateur et par film
🎮 GameBacklogprofiles, games, backlog_entriesbacklog_entries relie profil et jeu avec status (a_jouer, en_cours, termine) et rating
🎓 CampusHubprofiles, events, registrationsevents 1-N depuis l'organisateur ; registrations = jointure N-N étudiants ↔ événements

Remarquez que la table de jointure porte souvent de l'information utile : le statut dans GameBacklog, la date d'inscription dans CampusHub, le favori dans CinéList. Ce n'est pas un simple lien, c'est souvent l'entité centrale de l'espace personnel.

📜Migrations SQL

Une migration est un fichier SQL daté et versionné dans Git qui fait évoluer le schéma. On ne clique pas dans l'interface pour créer ses tables : on écrit (ou fait écrire) une migration, relue, commitée, rejouable.

-- supabase/migrations/..._create_watchlist.sql
create table public.films (
  id uuid primary key default gen_random_uuid(),
  title text not null,
  year integer,
  kind text not null check (kind in ('film', 'serie')),
  created_at timestamptz not null default now()
);

create table public.watchlist_items (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.profiles(id) on delete cascade,
  film_id uuid not null references public.films(id) on delete cascade,
  status text not null default 'a_voir' check (status in ('a_voir', 'vu')),
  is_favorite boolean not null default false,
  created_at timestamptz not null default now(),
  unique (user_id, film_id)
);

alter table public.films enable row level security;
alter table public.watchlist_items enable row level security;

Avec la CLI Supabase : supabase migration new create_watchlist crée le fichier, supabase db push l'applique au projet distant. Sans CLI, vous pouvez coller le SQL dans le SQL Editor du dashboard, mais gardez quand même le fichier dans supabase/migrations/ pour l'historique.

2Dans un second message, demandez-lui de critiquer sa propre proposition : doublons possibles, colonnes nullables à tort, relation N-N manquante, données dérivées stockées inutilement.

❌ À éviter

Une colonne favorite_films text dans profiles contenant « Dune, Alien, Heat » : impossible à filtrer, à compter ou à relier proprement.

✅ À faire

Une table watchlist_items avec is_favorite boolean : une ligne par couple utilisateur / film, filtrable et comptable dans le dashboard.

Chapitre 3 sur 6
🔐Supabase Auth : qui est connecté ?

Sans authentification, pas d'espace personnel, pas de watchlist à soi, pas de RLS. Supabase Auth gère les comptes dans le schéma auth ; votre application n'a qu'à appeler les bonnes méthodes.

MéthodeAppel supabase-jsUsage
Inscription e-mail / mot de passesupabase.auth.signUp({ email, password })Crée le compte ; un e-mail de confirmation est envoyé si l'option est active.
Connexion e-mail / mot de passesupabase.auth.signInWithPassword({ email, password })Ouvre une session.
Magic linksupabase.auth.signInWithOtp({ email })Envoie un lien de connexion sans mot de passe.
Déconnexionsupabase.auth.signOut()Supprime la session et les cookies.
Utilisateur courantsupabase.auth.getUser()Côté serveur, vérifie le jeton auprès de Supabase.

🔑 E-mail / mot de passe

Simple et attendu par les utilisateurs. Pensez aux messages d'erreur clairs (identifiants invalides, e-mail non confirmé) et au lien « mot de passe oublié ».

✉️ Magic link

Aucun mot de passe à retenir, pratique pour CampusHub. Le lien renvoie vers une URL de retour (/auth/callback) qui doit figurer dans Authentication > URL Configuration de Supabase.

🍪Session, cookies et middleware

Une session est composée d'un jeton d'accès (JWT) de courte validité et d'un jeton de rafraîchissement. Avec @supabase/ssr, elle est stockée dans des cookies : le serveur peut donc savoir qui fait la requête, dès le rendu de la page.

Le middleware (middleware.ts, renommé proxy.ts à partir de Next.js 16) s'exécute avant chaque requête : il crée un client serveur, appelle supabase.auth.getUser() pour rafraîchir la session si besoin et réécrit les cookies. Il peut aussi rediriger vers /login un visiteur non connecté qui tente d'ouvrir /dashboard.

⛔ Ne faites pas confiance à getSession() côté serveur Elle lit le cookie sans vérifier le jeton. Pour décider d'un accès côté serveur, utilisez getUser() (ou getClaims()), qui valide réellement l'utilisateur.

Protéger une page

// app/dashboard/page.tsx (Server Component)
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export default async function DashboardPage() {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) redirect('/login?next=/dashboard')
  // ici, user.id est fiable : on peut charger ses données
}

Le middleware fait une première barrière, la vérification dans la page (ou dans la Server Action) fait la seconde, et RLS dans la base fait la dernière. Trois couches, car chacune peut être contournée ou oubliée seule.

👤Profil lié à auth.users et redirection

La table auth.users appartient à Supabase : on n'y ajoute pas de colonnes métier. On crée une table public.profiles dont la clé primaire est aussi une clé étrangère vers auth.users(id).

create table public.profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  username text unique,
  avatar_url text,
  created_at timestamptz not null default now()
);

create function public.handle_new_user()
returns trigger
language plpgsql
security definer set search_path = ''
as $$
begin
  insert into public.profiles (id, username)
  values (new.id, new.raw_user_meta_data ->> 'username');
  return new;
end;
$$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute procedure public.handle_new_user();

Grâce au trigger, chaque inscription crée automatiquement son profil. Toutes vos tables métier (watchlist_items, backlog_entries, registrations) référencent ensuite profiles.id.

Redirection après connexion

  • Transmettez la page d'origine dans l'URL : /login?next=/events/b3f1…, puis redirigez vers next après succès (en vérifiant que c'est un chemin interne commençant par /).
  • Après un magic link, le route handler /auth/callback appelle exchangeCodeForSession(code) puis redirige vers /dashboard.
  • Un utilisateur déjà connecté qui ouvre /login est renvoyé directement vers son dashboard.
Auth = savoir qui ; RLS = décider ce qu'il peut faire.

L'authentification ne protège rien toute seule : elle fournit l'identité que les policies utiliseront au chapitre sécurité.

Chapitre 4 sur 6
✏️Les quatre opérations du CRUD

CRUD signifie Create, Read, Update, Delete : créer, lire, modifier, supprimer. C'est le cœur fonctionnel du socle : au moins une entité doit supporter les quatre, proprement.

Opérationsupabase-jsExemple fil rouge
Create.from('reviews').insert({ ... })CinéList : publier un avis noté sur un film
Read.from('backlog_entries').select('*, games(title)')GameBacklog : afficher mon backlog avec le titre de chaque jeu
Update.from('backlog_entries').update({ status: 'termine' }).eq('id', id)GameBacklog : passer un jeu en « terminé »
Delete.from('registrations').delete().eq('id', id)CampusHub : annuler une inscription
⛔ Un update ou un delete sans filtre Oublier .eq('id', id) ou filtrer sur une colonne trop large vise toutes les lignes autorisées. L'API Supabase refuse un update ou un delete sans aucun filtre, mais un filtre trop large passe : relisez toujours la requête générée par l'agent.
🛡️Valider côté client ET côté serveur

La validation côté client (attributs required, min, max, messages sous les champs) sert le confort de l'utilisateur. La validation côté serveur sert la sécurité : n'importe qui peut envoyer une requête sans passer par votre formulaire. Un même schéma Zod peut décrire la forme attendue des données et être réutilisé des deux côtés.

// app/films/actions.ts
'use server'
import { z } from 'zod'
import { revalidatePath } from 'next/cache'
import { createClient } from '@/lib/supabase/server'

const ReviewSchema = z.object({
  filmId: z.uuid(),
  rating: z.coerce.number().int().min(1).max(5),
  content: z.string().trim().max(1000).optional(),
})

export async function addReview(prevState: unknown, formData: FormData) {
  const parsed = ReviewSchema.safeParse(Object.fromEntries(formData))
  if (!parsed.success) return { error: "La note doit être comprise entre 1 et 5." }

  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return { error: "Connexion requise." }

  const { error } = await supabase.from('reviews').insert({
    user_id: user.id,
    film_id: parsed.data.filmId,
    rating: parsed.data.rating,
    content: parsed.data.content,
  })
  if (error) return { error: "Impossible d'enregistrer votre avis." }

  revalidatePath(`/films/${parsed.data.filmId}`)
  return { success: true }
}

Remarquez que user_id vient de la session, jamais d'un champ du formulaire : un utilisateur ne doit pas pouvoir publier au nom d'un autre.

🎛️Les états d'interface

Une interface générée par l'IA montre souvent seulement le cas où tout va bien. Une vraie application gère quatre états pour chaque liste et chaque formulaire.

⏳ Chargement

Squelette de liste via loading.tsx, bouton désactivé et libellé « Enregistrement… » pendant l'envoi (useActionState fournit un indicateur pending).

📭 Vide

« Votre backlog est vide. Ajoutez votre premier jeu » avec un bouton d'action, plutôt qu'une page blanche.

⚠️ Erreur

Message compréhensible près du champ ou du formulaire, sans afficher l'erreur SQL brute. error.tsx capture les erreurs de rendu d'une route.

✅ Succès

Confirmation visible (toast, message, redirection vers la fiche) et liste à jour.

Confirmer une suppression

Une suppression est irréversible : demandez confirmation dans une modale qui nomme l'élément (« Supprimer votre avis sur Dune ? »), avec un bouton destructif clairement identifié et un bouton d'annulation. La modale est un Client Component ; la suppression elle-même reste une Server Action qui revérifie l'utilisateur.

🔄Revalidation : afficher des données à jour

Next.js met en cache le rendu des pages. Après une mutation, il faut invalider ce cache pour que la liste reflète la modification : revalidatePath('/watchlist') dans la Server Action, ou revalidateTag si vous étiquetez vos requêtes. Sans cela, l'utilisateur ajoute un film et… ne le voit pas apparaître.

❌ À éviter

Forcer un window.location.reload() après chaque ajout, ou dupliquer la liste dans un state client qui finit par diverger de la base.

✅ À faire

Server Action → écriture → revalidatePath des pages concernées (liste et dashboard) → retour d'un état succès affiché par le formulaire.

Un CRUD fini = 4 opérations × 4 états, validés deux fois.

Faites de cette phrase un critère d'acceptation dans chaque ticket CRUD confié à l'agent.

🛡️Row Level Security : la base décide

Avec Supabase, le navigateur peut interroger la base directement grâce à la clé anon. Ce qui empêche un étudiant de lire la watchlist d'un autre, ce n'est pas votre interface : ce sont les règles RLS dans Postgres.

  • RLS activé (alter table ... enable row level security) et aucune policy : plus personne ne peut lire ni écrire via l'API. C'est l'état sûr par défaut.
  • Policy : une règle qui autorise une opération (select, insert, update, delete) pour un rôle, sous condition.
  • auth.uid() : fonction qui renvoie l'id de l'utilisateur authentifié à l'origine de la requête ; c'est la brique de presque toutes vos conditions.
  • using (...) filtre les lignes existantes visibles ou modifiables ; with check (...) vérifie les lignes écrites (insert, update).
create policy "Lire ses entrées de watchlist"
on public.watchlist_items for select
to authenticated
using ( (select auth.uid()) = user_id );

create policy "Ajouter dans sa propre watchlist"
on public.watchlist_items for insert
to authenticated
with check ( (select auth.uid()) = user_id );

create policy "Modifier ses entrées"
on public.watchlist_items for update
to authenticated
using ( (select auth.uid()) = user_id )
with check ( (select auth.uid()) = user_id );

create policy "Supprimer ses entrées"
on public.watchlist_items for delete
to authenticated
using ( (select auth.uid()) = user_id );

Écrire (select auth.uid()) plutôt que auth.uid() seul est la forme recommandée par Supabase : la valeur est calculée une fois par requête au lieu d'une fois par ligne.

🔑Clés et secrets

🟢 Clé anon

Publique, présente dans le navigateur via NEXT_PUBLIC_SUPABASE_ANON_KEY. Elle agit avec les rôles anon ou authenticated : soumise à RLS.

🔴 Clé service_role

Secrète (SUPABASE_SERVICE_ROLE_KEY), contourne RLS. Uniquement côté serveur, pour des scripts d'administration. Jamais préfixée NEXT_PUBLIC_, jamais dans un Client Component.

  • .env.local est listé dans .gitignore (c'est le cas par défaut avec npx create-next-app@latest) : vérifiez-le avant le premier git add.
  • Fournissez un .env.example avec les noms des variables et des valeurs vides, pour documenter sans exposer.
  • Si une clé secrète a été commitée, la supprimer du fichier ne suffit pas : elle reste dans l'historique. Il faut la régénérer dans Supabase.
Et les nouvelles clés « publishable » et « secret » de Supabase ?
Supabase propose désormais des clés au format sb_publishable_... et sb_secret_... en complément des clés anon et service_role historiques. La logique est identique : la clé publishable est publique et soumise à RLS, la clé secret contourne RLS et reste côté serveur. Utilisez les noms de variables que votre projet et AGENTS.md ont fixés, et restez cohérent.
⛔ Interdit Utiliser la clé service_role « pour que ça marche » quand une requête est bloquée par RLS. Le blocage signale une policy manquante : c'est la policy qu'il faut écrire.

🔎Requêtes filtrées, recherche et tri

Le socle exige une recherche ou un filtrage. Avec supabase-js, on enchaîne des filtres sur la requête, et on garde les critères dans l'URL pour qu'une recherche soit partageable et survive au rechargement.

// app/films/page.tsx (Server Component)
export default async function FilmsPage({ searchParams }: {
  searchParams: Promise<{ q?: string; kind?: string; page?: string }>
}) {
  const { q = '', kind, page = '1' } = await searchParams
  const pageSize = 10
  const from = (Number(page) - 1) * pageSize
  const to = from + pageSize - 1

  const supabase = await createClient()
  let query = supabase
    .from('films')
    .select('id, title, year, kind', { count: 'exact' })
    .ilike('title', `%${q}%`)
    .order('title', { ascending: true })
    .range(from, to)
  if (kind) query = query.eq('kind', kind)

  const { data: films, count, error } = await query
  // afficher la liste, l'état vide, et la pagination à partir de count
}
  • .eq('status', 'en_cours') : égalité stricte, pour les filtres à valeurs fixes (statut GameBacklog, type film / série).
  • .ilike('title', '%dune%') : recherche partielle insensible à la casse ; les % signifient « n'importe quels caractères ».
  • .order('created_at', { ascending: false }) : tri, ici les plus récents d'abord.
  • .range(0, 9) : pagination, bornes incluses, donc 10 résultats ; { count: 'exact' } renvoie le total pour calculer le nombre de pages.
📊Le dashboard personnel

Le dashboard est l'espace personnel exigé par le socle : il résume l'activité de l'utilisateur connecté. Des compteurs simples suffisent, obtenus sans charger les lignes grâce à head: true.

const [toWatch, seen, favorites] = await Promise.all([
  supabase.from('watchlist_items').select('*', { count: 'exact', head: true })
    .eq('user_id', user.id).eq('status', 'a_voir'),
  supabase.from('watchlist_items').select('*', { count: 'exact', head: true })
    .eq('user_id', user.id).eq('status', 'vu'),
  supabase.from('watchlist_items').select('*', { count: 'exact', head: true })
    .eq('user_id', user.id).eq('is_favorite', true),
])

🎫Découper le socle en tickets pour l'agent

Demander « construis-moi l'application » produit un gros bloc impossible à relire. Un agent travaille bien sur des tâches petites, ordonnées, avec un critère de fin vérifiable.

Schéma→Auth→CRUD entité 1→Relation→Recherche→Dashboard

Cet ordre respecte les dépendances : pas de CRUD sans tables, pas de données personnelles sans utilisateur, pas de dashboard sans données. Chaque ticket s'appuie sur le précédent, déjà testé et commité.
