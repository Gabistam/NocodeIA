Prompt de départ

[Contexte]
Je construis le MVP de mon projet (voir PROJECT.md, DESIGN.md et AGENTS.md à la racine du repo). Stack : Next.js App Router + TypeScript, Supabase (Postgres, Auth, RLS) via @supabase/ssr, déploiement Vercel.

[Rôle]
Agis comme un développeur back-end senior spécialisé Postgres et Supabase, exigeant sur la sécurité.

[Objectif / Action]
1. Propose un modèle de données pour le socle du MVP : entités, colonnes typées, clés primaires uuid, clés étrangères, relations 1-N et N-N, contraintes (not null, unique, check).
2. Critique ensuite ta propre proposition : doublons possibles, colonnes mal typées, relations manquantes, données dérivées stockées inutilement.
3. Propose les policies RLS pour chaque table, opération par opération (select, insert, update, delete), en utilisant (select auth.uid()).
4. Découpe la construction en tickets ordonnés (schéma → auth → CRUD entité 1 → relation → recherche → dashboard), avec pour chacun un critère « terminé quand ».

[Contraintes]
- Une table public.profiles liée à auth.users(id), créée par trigger à l'inscription.
- RLS activé sur toutes les tables ; aucune utilisation de la clé service_role côté client.
- Ne génère aucun code pour l'instant : uniquement le contenu de data-model.md et la liste des tickets.
- Pose-moi d'abord les questions nécessaires si une règle métier est ambiguë.

[Exemple de format attendu]
## Entités
- watchlist_items : id uuid PK, user_id uuid FK → profiles.id, film_id uuid FK → films.id, status text check (a_voir, vu), is_favorite boolean
## Règles RLS
- watchlist_items : select/insert/update/delete si (select auth.uid()) = user_id
## Tickets
- T1 — Migrations + RLS — terminé quand les tables sont visibles et RLS actif partout

Exemple corrigé — CinéList
# data-model.md — CinéList

## Entités
- profiles — profil public de l'utilisateur, lié à auth.users
- films — catalogue partagé de films et séries
- watchlist_items — films suivis par un utilisateur (statut, favori)
- reviews — avis notés d'un utilisateur sur un film

## Champs
- profiles : id uuid PK FK → auth.users.id on delete cascade, username text unique, avatar_url text, created_at timestamptz default now()
- films : id uuid PK default gen_random_uuid(), title text not null, year integer, kind text not null check (kind in ('film', 'serie')), poster_url text, created_at timestamptz default now()
- watchlist_items : id uuid PK default gen_random_uuid(), user_id uuid not null FK → profiles.id on delete cascade, film_id uuid not null FK → films.id on delete cascade, status text not null default 'a_voir' check (status in ('a_voir', 'vu')), is_favorite boolean not null default false, created_at timestamptz default now()
- reviews : id uuid PK default gen_random_uuid(), user_id uuid not null FK → profiles.id on delete cascade, film_id uuid not null FK → films.id on delete cascade, rating integer not null check (rating between 1 and 5), content text check (char_length(content) between 0 and 1000), created_at timestamptz default now(), updated_at timestamptz

## Relations
- auth.users 1-1 profiles (profiles.id = auth.users.id), créé par le trigger on_auth_user_created
- profiles N-N films via watchlist_items
- profiles 1-N reviews (reviews.user_id)
- films 1-N reviews (reviews.film_id)

## Contraintes et règles métier
- unique (user_id, film_id) sur watchlist_items : un film une seule fois par watchlist
- unique (user_id, film_id) sur reviews : un seul avis par utilisateur et par film
- rating entre 1 et 5 ; content optionnel, 1000 caractères maximum
- user_id est toujours lu depuis la session côté serveur, jamais depuis le formulaire

## Règles RLS (RLS activé sur toutes les tables)
- profiles : select pour authenticated ; update si (select auth.uid()) = id ; pas d'insert via l'API (trigger)
- films : select pour authenticated ; aucune écriture via l'API (catalogue alimenté par migration de seed)
- watchlist_items : select, insert (with check), update (using + with check), delete si (select auth.uid()) = user_id
- reviews : select pour authenticated (avis publics) ; insert, update, delete si (select auth.uid()) = user_id

## Index utiles
- watchlist_items (user_id, status) pour le dashboard et les filtres
- reviews (film_id) pour la fiche film

## Points ouverts / décisions (voir AI-LOG.md)
- Catalogue : saisi par migration de seed pour le MVP ; import depuis une API externe reporté en bonus
- Un avis supprimé n'est pas archivé (suppression définitive, confirmée par modale)
- Isolation testée avec deux comptes : le compte B ne voit ni ne modifie la watchlist du compte A
