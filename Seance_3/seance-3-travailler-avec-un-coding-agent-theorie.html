Chapitre 1 sur 6
🤖Qu'est-ce qu'un coding agent ?

En séance 1, vous avez distingué le chat (l'IA répond, vous copiez-collez) de l'agent (l'IA agit dans votre projet). Un coding agent est un modèle de langage équipé d'outils : il lit vos fichiers, les modifie, lance des commandes dans le terminal et observe le résultat, jusqu'à atteindre l'objectif demandé.

Objectif du chapitreComprendre ce que fait réellement un agent quand vous lui confiez une tâche, pour savoir quoi lui autoriser, quoi lui fournir et quoi vérifier.

La boucle agentique

Un agent ne répond pas en une fois : il enchaîne des tours d'une même boucle, et chaque tour s'appuie sur le résultat du précédent.

Observer→Planifier→Agir→Vérifier→Observer…
  • Observer : lire la demande, les fichiers d'instructions, l'arborescence, le code existant.
  • Planifier : découper l'objectif en étapes (quels fichiers créer ou modifier, dans quel ordre).
  • Agir : écrire du code, créer un fichier, lancer une commande (npm install, npm run lint).
  • Vérifier : lire la sortie de la commande, l'erreur de compilation, le résultat d'un test, puis décider de continuer, corriger ou s'arrêter.

Cette boucle est la force de l'agent (il corrige seul une erreur de typage) et sa faiblesse (il peut tourner longtemps dans la mauvaise direction si l'objectif est flou).

🧰Les outils de l'agent

Ce qui distingue un agent d'un chat, ce sont ses outils : des actions qu'il peut déclencher lui-même.

📂 Fichiers

Lire, créer, modifier, parfois supprimer des fichiers du projet. Exemple : créer app/ma-liste/page.tsx pour CinéList.

💻 Terminal

Exécuter des commandes : installer une dépendance, lancer npm run build, faire un git status.

🔎 Recherche

Chercher dans le code (où est utilisé ce composant ?), parfois sur le web ou dans une documentation.

Les modes de permission

Chaque outil comporte un risque : une commande peut supprimer un dossier, une modification peut écraser votre travail. Les agents proposent donc des modes de permission qui fixent ce que l'agent peut faire sans vous demander.

ALecture seule / plan — l'agent explore et propose, il ne modifie rien.Sûr
BApprobation à chaque action — chaque modification et chaque commande attend votre accord.Recommandé au début
CÉditions automatiques — les fichiers sont modifiés sans confirmation, les commandes restent soumises à accord.Avec Git propre
DAccès total — tout est exécuté sans confirmation.Risqué

Les noms varient selon l'outil (Claude Code, Codex, Cursor, Copilot…), mais la logique est la même. Règle simple : plus vous montez en autonomie, plus votre dépôt Git doit être propre avant de lancer l'agent.

⛔ Piège Accepter toutes les actions « pour aller plus vite » sans lire. C'est exactement ainsi qu'un agent installe une dépendance inutile ou réécrit un fichier que vous aviez corrigé à la main.
📜Fichiers d'instructions et types d'agents

À chaque nouvelle session, l'agent repart de zéro. Il lit donc automatiquement un fichier d'instructions placé à la racine du projet : c'est votre AGENTS.md de la séance 2.

  • AGENTS.md : format ouvert lu par de nombreux agents (Codex, Cursor, Copilot, OpenCode…).
  • CLAUDE.md : fichier lu par Claude Code. Pour éviter de maintenir deux fichiers, il peut simplement contenir la ligne @AGENTS.md, qui importe son contenu.
  • Contenu attendu : stack, commandes utiles, conventions de code, règles (« ne jamais committer de secret »), renvoi vers PROJECT.md et DESIGN.md.

CLI, IDE ou cloud ?

TypeOù il tournePoints fortsVigilance
CLI (Claude Code, Codex CLI, OpenCode)Dans votre terminal, sur votre machineAccès direct au projet et aux commandes, très scriptableLes diffs se lisent dans le terminal ou via Git
IDE (Cursor, Copilot en mode agent, Antigravity)Dans l'éditeur de codeDiffs visuels, acceptation fichier par fichierTentation d'accepter en bloc
Cloud (agents asynchrones)Sur un serveur distant, à partir de votre dépôt GitHubTravaille en parallèle, livre une branche ou une pull requestRelire la pull request avant fusion, ne pas lui confier de secrets
L'outil change, la méthode reste.

Boucle, outils, permissions, fichier d'instructions : ces quatre notions existent dans tous les agents. Si vous les maîtrisez, vous changerez d'outil sans changer de méthode.

Chapitre 2 sur 6
🚀Créer le projet Next.js

Avant de confier quoi que ce soit à l'agent, vous posez vous-même une base saine : un projet Next.js généré par l'outil officiel, avec la stack décidée dans votre PROJECT.md.

Objectif du chapitreObtenir un projet Next.js qui démarre, comprendre sa structure et y déposer vos fichiers de contexte pour que l'agent travaille dans le bon cadre.

La commande

npx create-next-app@latest cinelist

Réponses recommandées aux questions :
TypeScript ............ Yes
ESLint ................ Yes
Tailwind CSS .......... Yes
App Router ............ Yes
Alias d'import (@/*) .. Yes (valeur par défaut)

Vous pouvez aussi passer les options directement : npx create-next-app@latest cinelist --typescript --tailwind --eslint --app. L'outil installe les dépendances et, en général, initialise un dépôt Git avec un premier commit.

1Lancer la commande dans le dossier où vous rangez vos projets.
2Entrer dans le dossier : cd cinelist.
3Démarrer le serveur de développement : npm run dev, puis ouvrir http://localhost:3000.
4Vérifier que la compilation de production passe aussi : npm run build.
Pourquoi ne pas laisser l'agent tout créer ?Vous pouvez demander à l'agent de lancer la commande, mais c'est l'étape la plus simple et la plus standard du projet. La faire vous-même garantit une base officielle, sans configuration « inventée », et vous apprend ce que contient le projet.
🗂️La structure du projet

Avec l'App Router, l'arborescence du dossier app/ définit les routes : chaque dossier contenant un page.tsx devient une URL.

cinelist/
├── app/
│   ├── layout.tsx        mise en page commune (header, polices)
│   ├── page.tsx          route /
│   ├── globals.css       import de Tailwind + variables
│   └── ma-liste/
│       └── page.tsx      route /ma-liste
├── components/          à créer : composants réutilisables
├── lib/                 à créer : fonctions utilitaires, données, clients
├── public/               images et fichiers statiques
├── package.json          dépendances et scripts npm
├── .gitignore
├── PROJECT.md  DESIGN.md  AGENTS.md
└── AI-LOG.md

📦 package.json

Liste les dépendances et les scripts (dev, build, start, lint). C'est le premier fichier à relire quand un agent ajoute une bibliothèque.

🎨 Tailwind CSS

Framework de classes utilitaires. Les couleurs, rayons et espacements de votre DESIGN.md doivent y être traduits, pas réinventés à chaque page.

🧱 components/

Ce dossier n'est pas créé automatiquement. Exemple : components/GameCard.tsx pour GameBacklog, réutilisé sur plusieurs pages.

🔐 .env.local

Fichier des variables d'environnement locales (clés Supabase en S4). Il ne doit jamais être versionné.

📎Donner le contexte à l'agent

Copiez à la racine du projet vos trois fichiers de la séance 2 : PROJECT.md, DESIGN.md, AGENTS.md. Complétez AGENTS.md avec ce que vous savez maintenant : commandes réelles du projet et structure des dossiers.

Première interaction avec l'agent : aucune modification. Vous lui demandez de lire et de reformuler.

Contexte : projet Next.js (App Router, TypeScript, Tailwind) fraîchement créé.
Action : lis PROJECT.md, DESIGN.md et AGENTS.md, puis parcours app/.
Contraintes : ne modifie aucun fichier, ne lance aucune installation.
Résultat attendu : un résumé en 10 lignes maximum du projet, de la stack,
des conventions et des incohérences ou manques que tu repères dans ces fichiers.

Si le résumé est faux ou incomplet, le problème vient de vos fichiers : corrigez-les maintenant, avant toute génération de code. C'est beaucoup moins coûteux que de corriger dix fichiers générés sur une mauvaise compréhension.

❌ À éviter

« Voilà mon projet, fais la page d'accueil de CampusHub. » L'agent n'a rien lu et invente un design.

✅ À faire

« Lis les fichiers de contexte et résume-les. » Puis, une fois le résumé validé, une première tâche cadrée.

Chapitre 3 sur 6
🛟Pourquoi Git est indispensable avec un agent

Un agent peut modifier dix fichiers en une seule réponse. Sans Git, vous ne savez ni ce qui a changé, ni comment revenir à l'état qui marchait. Git est votre filet de sécurité : chaque étape validée devient un point de sauvegarde.

Objectif du chapitreMaîtriser les commandes Git utiles au travail avec un agent : voir, enregistrer, isoler, annuler, publier.

Les commandes du quotidien

CommandeRôleQuand l'utiliser
git initCrée un dépôt Git dans le dossierUne fois, si create-next-app ne l'a pas fait
git statusListe les fichiers modifiés, ajoutés, non suivisAvant et après chaque tâche de l'agent
git diffAffiche ligne par ligne les modifications non indexéesPour relire ce que l'agent a changé
git add .Indexe les modifications pour le prochain commitAprès relecture du diff
git commit -m "..."Enregistre un point de sauvegarde avec un messageAprès chaque étape validée
git log --onelineAffiche l'historique des commitsPour retrouver un état antérieur
Une étape validée = un commit.

Tâche terminée, diff relu, page vérifiée : vous committez. Vous repartez ainsi toujours d'un état propre et connu avant la tâche suivante.

🌿Branches et retour arrière

Une branche isole un travail en cours : si l'agent part dans une mauvaise direction, la branche principale reste intacte.

git switch -c feature/ma-liste   crée la branche et s'y place
... travail de l'agent, relecture, commits ...
git switch main                   revient sur la branche principale
git merge feature/ma-liste        intègre le travail validé

Revenir en arrière : restore ou revert ?

↩️ git restore

Annule des modifications non committées d'un fichier : git restore app/page.tsx. Pour désindexer sans perdre le travail : git restore --staged app/page.tsx. Idéal quand l'agent vient de casser un fichier.

🔁 git revert

Crée un nouveau commit qui annule un commit existant : git revert <hash>. L'historique est conservé : c'est la méthode sûre pour un commit déjà poussé sur GitHub.

⛔ Attention git restore efface définitivement les modifications non committées du fichier. Vérifiez avec git diff que vous ne jetez pas aussi votre propre travail.
Et git reset --hard ?
Cette commande remet tout le dépôt à un état antérieur et supprime les modifications en cours, sans retour possible. Elle existe, mais un agent ne devrait jamais la lancer sans votre accord explicite : interdisez-la dans AGENTS.md.
☁️Publier sur GitHub et protéger les secrets

Créez un dépôt vide sur GitHub (sans README, votre projet en a déjà un), puis reliez votre dépôt local au dépôt distant :

git remote add origin https://github.com/<votre-compte>/cinelist.git
git branch -M main
git push -u origin main

Si vous utilisez la CLI GitHub, gh repo create fait la même chose en une commande interactive. Ensuite, un simple git push publie vos nouveaux commits.

.gitignore et .env

Le fichier .gitignore liste ce que Git ne doit jamais suivre : node_modules/, .next/ et surtout les fichiers .env*. En S4, votre .env.local contiendra NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY et éventuellement SUPABASE_SERVICE_ROLE_KEY, clé qui contourne toute la sécurité de la base.

  • Ouvrez .gitignore et vérifiez la présence d'une ligne couvrant les .env.
  • Avant chaque commit, git status ne doit jamais afficher de fichier .env.
  • Une clé poussée sur GitHub est compromise, même si vous supprimez le commit ensuite : il faut la régénérer.

Chapitre 4 sur 6
🧭Le cycle explorer → planifier → coder → vérifier

Piloter un agent, c'est découper le travail et contrôler chaque passage de relais. Vous ne demandez pas « fais l'application » : vous enchaînez des cycles courts, chacun avec un objectif unique.

Objectif du chapitreSavoir formuler une tâche agent structurée, obtenir un plan avant le code et valider le résultat sur des critères de fin explicites.
1

Explorer

L'agent lit les fichiers concernés et vous dit ce qu'il a compris.

« Quels fichiers sont concernés ? »
2

Planifier

L'agent propose un plan numéroté, vous le corrigez ou le validez.

« Quelles étapes, dans quel ordre ? »
3

Coder

L'agent exécute le plan validé, et seulement lui.

« Qu'est-ce qui change ? »
4

Vérifier

Build, lint, affichage, relecture du diff, puis commit.

« Comment je sais que c'est fini ? »

Le mode plan

La plupart des agents proposent un mode plan : l'agent peut lire et raisonner, mais pas modifier. Dans Claude Code, on y accède avec Maj+Tab, qui fait défiler les modes jusqu'au mode plan ; Cursor, Codex ou Copilot proposent un équivalent. Sans ce mode, écrivez simplement : « Propose un plan, n'écris aucun code tant que je n'ai pas validé. »

Relire un plan, c'est vérifierLes fichiers cités existent-ils ? Le plan respecte-t-il DESIGN.md ? Ajoute-t-il une dépendance ? Touche-t-il à des fichiers hors du périmètre ? Un plan corrigé coûte une phrase ; un code corrigé coûte une session.
🎯Une tâche = un objectif

Une petite itération produit un résultat vérifiable et committable. Plus la tâche est large, plus l'agent prend de décisions à votre place.

❌ Trop large

« Fais GameBacklog avec l'authentification, les jeux, les notes et le dashboard. »

✅ Une itération

« Crée la page statique /mes-jeux qui affiche 6 jeux fictifs en cartes, selon DESIGN.md. »

Les critères de fin

Un critère de fin est une condition observable qui permet de dire « terminé » sans discussion. Il se rédige avant de lancer l'agent.

  • npm run build et npm run lint passent sans erreur.
  • La page /evenements de CampusHub affiche au moins 4 événements fictifs.
  • Les couleurs et rayons utilisés sont ceux de DESIGN.md.
  • Aucune nouvelle dépendance dans package.json.
  • L'affichage reste lisible en largeur mobile.
📝Le prompt de tâche agent

Les 5 Piliers de la séance 1 s'adaptent au travail agentique. Un prompt de tâche structuré, idéalement enregistré dans un fichier tache.md, contient six rubriques :

# Objectif
Créer la page statique /ma-liste de CinéList.
# Contexte (fichiers à lire)
PROJECT.md, DESIGN.md, AGENTS.md, app/layout.tsx
# Contraintes
TypeScript strict, Tailwind uniquement, composants dans components/
# Étapes attendues
1. Proposer un plan  2. Attendre validation  3. Coder  4. Lancer build et lint
# Critères de fin
Build et lint OK, 6 films affichés, conforme DESIGN.md, responsive
# Interdits
Aucune dépendance ajoutée, aucun fichier supprimé, pas de Supabase

Relire le diff avant de committer

La vérification finale, c'est vous. Lisez git diff ou le diff de votre IDE fichier par fichier : chaque modification doit s'expliquer par la tâche. Une ligne inattendue dans package.json ou un fichier modifié hors périmètre est un signal d'alerte, même si la page s'affiche correctement.

Chapitre 5 sur 6
🧠La fenêtre de contexte se remplit

Tout ce que l'agent lit ou produit pendant une session s'accumule dans sa fenêtre de contexte : vos messages, les fichiers ouverts, les sorties de commandes, ses propres réponses. Cette mémoire de travail est limitée.

Objectif du chapitreReconnaître une session saturée, savoir la compacter ou la relancer, et capitaliser ce que vous apprenez dans AGENTS.md et AI-LOG.md.

Symptômes d'une session saturée

  • L'agent oublie une consigne donnée au début (il réutilise une couleur interdite par DESIGN.md).
  • Il repropose une solution déjà rejetée.
  • Il mélange deux tâches (la page « Mes jeux » et le formulaire de note de GameBacklog).
  • L'outil signale que le contexte est presque plein ou qu'il a été compacté automatiquement.

🗜️ Compacter

La compaction remplace l'historique par un résumé. Dans Claude Code : /compact, avec éventuellement une consigne sur ce qu'il faut garder. D'autres agents proposent un équivalent ou le font automatiquement.

🆕 Nouvelle session

Une tâche terminée et committée ? Repartez d'une session vierge (/clear dans Claude Code, nouvelle conversation ailleurs). AGENTS.md sera relu, sans le bruit de la tâche précédente.

Une nouvelle tâche, une nouvelle session.

Le contexte utile doit vivre dans vos fichiers (PROJECT.md, DESIGN.md, AGENTS.md, tache.md), pas dans l'historique d'une conversation.

🔧Faire évoluer AGENTS.md

Quand vous corrigez deux fois la même erreur, ce n'est plus un accident : c'est une règle manquante. Ajoutez-la à AGENTS.md pour que toutes les sessions futures en profitent.

Erreur répétéeRègle ajoutée dans AGENTS.md
L'agent écrit des couleurs en dur (#3b82f6) au lieu des tokens« Utiliser uniquement les couleurs définies dans DESIGN.md, jamais de valeur hexadécimale en dur. »
Il crée des composants dans app/« Les composants réutilisables vont dans components/. »
Il conclut sans vérifier« Avant de conclure, lancer npm run lint et npm run build et montrer la sortie. »
Il installe des paquets sans demander« Ne jamais ajouter de dépendance sans validation explicite. »

Gardez AGENTS.md court et concret : une règle par ligne, formulée comme une consigne vérifiable. Committez chaque modification de ce fichier comme n'importe quel code.

📓AI-LOG.md, le journal des décisions

AI-LOG.md garde la trace de votre travail avec l'IA. Il est évalué dans la note « méthodologie IA » et vous servira en S5 pour expliquer vos choix.

## 2026-10-06 — Page statique « Ma liste »
Outil : Claude Code (mode plan puis approbation manuelle)
Prompt : voir tache.md (objectif, contexte, contraintes, critères, interdits)
Résultat : app/ma-liste/page.tsx + components/FilmCard.tsx + lib/films.ts
Vérification : build OK, lint OK, test en largeur mobile, diff relu
Décision : accepté ; couleur du badge corrigée à la main ; règle ajoutée
dans AGENTS.md ; commit « feat: page statique Ma liste »
  • Une entrée par tâche, datée, rédigée juste après la vérification.
  • La décision est la rubrique la plus importante : accepté, modifié, rejeté, et pourquoi.
  • Pas de copie intégrale des conversations : un résumé du prompt ou un renvoi vers tache.md suffit.

Chapitre 6 sur 6
⚠️Six dérives fréquentes

Un agent est optimisé pour avancer. Sans cadre, il en fait trop, insiste quand il se trompe ou déclare victoire trop tôt. Connaître ces dérives permet de les repérer dans un diff ou dans une réponse.

Objectif du chapitreIdentifier les dérives typiques d'un coding agent et appliquer pour chacune une contre-mesure concrète.

📈 Scope creep

Vous demandez une page « Ma liste » ; l'agent ajoute aussi un système de notes, refait le header et renomme des fichiers. Chaque ajout non demandé est du code à relire et un risque de régression.

🔄 Boucle de corrections

L'agent corrige une erreur, en crée une autre, revient à la première… Sur GameBacklog, il alterne entre deux façons de typer un statut sans jamais converger.

📦 Dépendances inventées ou inutiles

Installation d'une bibliothèque pour une tâche que Tailwind ou React font déjà, voire d'un paquet au nom plausible mais inexistant ou malveillant.

🗑️ Suppression ou réécriture

L'agent réécrit entièrement un fichier que vous aviez corrigé à la main, ou supprime un fichier qu'il juge inutile.

🎭 « Ça marche » sans preuve

L'agent annonce « tout fonctionne » sans avoir lancé le build, ni ouvert la page. L'affirmation n'est pas une vérification.

🔑 Secrets dans le code

Une clé écrite en dur dans un composant, ou un .env ajouté au commit. Sur CampusHub, une clé de service exposée donne accès à toutes les inscriptions.

🛡️Les contre-mesures
DériveContre-mesure
Scope creepUne tâche = un objectif ; rubrique « Interdits » ; refuser dans le diff ce qui n'était pas demandé.
Boucle de correctionsArrêter l'agent après deux échecs sur le même problème, revenir au dernier commit (git restore), reformuler la tâche plus petite, ouvrir une nouvelle session.
